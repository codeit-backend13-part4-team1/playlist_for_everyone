# 11. 이력·재시도 운영 설정

현재 값은 운영 부하를 측정하기 전의 초기값입니다.
기능의 검증 결과와 운영 용량이 충분하다는 판단을 구분합니다.

## 설정값과 환경 구분

설정은 `everyone.sse` 아래에 있습니다.

| 설정 | 환경변수 | 기본값 |
| --- | --- | --- |
| `history.key-prefix` | `EVERYONE_SSE_HISTORY_KEY_PREFIX` | 프로필별 아래 표 |
| `history.retention` | `EVERYONE_SSE_HISTORY_RETENTION` | `10m` |
| `history.max-events-per-user` | `EVERYONE_SSE_HISTORY_MAX_EVENTS_PER_USER` | `1000` |
| `retry.initial-delay` | `EVERYONE_SSE_RETRY_INITIAL_DELAY` | `1s` |
| `retry.max-delay` | `EVERYONE_SSE_RETRY_MAX_DELAY` | `30s` |
| `retry.max-retries` | `EVERYONE_SSE_RETRY_MAX_RETRIES` | `3` |

보관기간과 재시도 간격은 1ms 이상, 건수와 재시도 횟수는 1 이상입니다.
최대 재시도 간격은 초기 간격 이상이어야 합니다. 허용 범위 밖이면 설정 바인딩 시 시작에 실패합니다.

| 설정 파일 | 이력 접두사 기본값 |
| --- | --- |
| 공통 설정 | `everyone:sse:history` |
| dev | `everyone:dev:sse:history` |
| prod | `everyone:prod:sse:history` |
| test | `everyone:test:sse:history` |

dev·prod의 명시적 환경변수 값은 기본값보다 우선합니다.
테스트 프로필에는 테스트 전용 값을 명시하며 개별 통합 테스트는 더 구체적인 전용 접두사를 지정할 수 있습니다.
같은 환경의 모든 서버는 **같은 Redis·이력 접두사·Pub/Sub 채널**을 사용해야 합니다.

키 접두사 분리는 저장 데이터의 구분입니다. 채널까지 자동으로 분리하지 않습니다.
환경을 나누려면 채널 또는 Redis도 구분합니다.
접두사를 변경하면 이전 키가 자동으로 이동하지 않고 기존 커서를 새 접두사에서 찾지 못할 수 있습니다.
서버마다 서로 다른 접두사를 읽는 배포 상태를 피하고, 기존 키의 잔여 TTL과 복구 범위를 고려합니다.

## 메모리와 보관 정책 조정

`1000건`은 전체 상한이 아닌 사용자별 상한입니다.
예를 들어 이력을 가진 사용자 1만 명이 각각 상한에 도달하면 이벤트만 최대 1천만 건이며 UUID 매핑도 필요합니다.
실제 메모리는 데이터 크기·Redis 내부 구조·활성 사용자 수에 따라 달라집니다.

| 관찰 대상 | 조정할 때 볼 내용 |
| --- | --- |
| 이력을 가진 사용자 수·사용자별 발생량 | 활성 사용자 증가 시 총 키·항목 증가 |
| 평균·상위 이벤트 크기 | 같은 건수라도 payload가 크면 더 많은 메모리 사용 |
| Redis 메모리·eviction·명령 지연 | 보관기간·건수와 인프라 용량 검토 |
| 만료·건수 제한으로 복구 불가능한 범위 | 서비스가 요구하는 재연결 복구 시간과 비교 |
| 조회 실패·재시도 소진 | Redis·DB 원인과 지연을 확인한 뒤 재시도 설정 조정 |

시간과 건수 중 먼저 도달하는 제한 때문에 복구 범위가 짧아질 수 있습니다.
이 표는 운영에서 측정할 항목이며, 모든 항목의 전용 메트릭 수집이 구현되어 있다는 뜻은 아닙니다.
신규 저장의 TTL 갱신과 개별 이벤트 정리는 [보관 정책](09-shared-history.md#보관기간건수키-ttl)을 참고합니다.

## 실패 로그를 읽는 순서

| 위치 | 현재 로그와 확인할 내용 |
| --- | --- |
| 초기 조회 실패 | `ERROR`와 원인 예외, HTTP `503`. 현재 로그에 사용자·연결 ID는 없음 |
| 일반 후속 전송 실패 | `WARN`, 신호의 이벤트 ID·수신자 ID·연결 ID |
| 예약 작업 전송 실패 | `WARN`, 사용자·연결 ID |
| 재시도 소진 | `WARN`, 사용자·연결 ID·최대 횟수·원인 예외 |
| 식별된 클라이언트 단절 | `DEBUG`, 스택 제외 |
| 후속 기준 위치 미확인 | `DEBUG`, 기준 위치와 남은 건수. 그 자체는 조회 실패가 아님 |

일시적 조회 실패마다 별도의 WARN을 남기는 것은 아닙니다.
Redis 브로커 발행·수신과 알림 리스너 로그는 [전송 로그](06-redis-transport.md#실패-처리와-로그)를 함께 확인합니다.
연결된 신호의 이벤트 ID가 실제로 실패한 이력 항목의 ID와 항상 같다고 가정하지 않습니다.
메시지 본문을 로그 추적용으로 추가하지 않습니다.

## 전달 보장의 경계

- DB 알림 커밋, Redis 이력 저장, Pub/Sub 발행은 하나의 원자적 작업이 아닙니다.
- 이력 저장 전에 실패하면 DB에는 알림이 있어도 이력 복구 대상에는 없을 수 있습니다.
- 이력 저장 후 발행 실패 시 이력은 남지만 자동 재발행은 없습니다.
- 보관된 이벤트는 이후 조회 신호나 유효한 커서를 가진 재연결에서 처리될 수 있습니다. 즉시 전달을 보장하지 않습니다.
- Pub/Sub 재구독 자체가 모든 살아 있는 SSE 연결의 후속 조회를 자동 실행하는 것은 아닙니다.
- 브라우저 수신 ACK, Outbox, 모든 장애 상황의 정확히 한 번 전달은 제공하지 않습니다.

후속 조회 재시도는 최초 실패한 조회를 제한적으로 다시 수행하는 기능입니다.
브로커 발행 재시도나 브라우저 재연결 정책과 구분해서 운영합니다.
