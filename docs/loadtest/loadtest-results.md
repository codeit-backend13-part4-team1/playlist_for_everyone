판단: 테스트 설정이 아니라 **플레이리스트 목록 쿼리·인덱스 문제**. 이슈 #22에서 아래 후보를 적용하고 재측정함 (아래 "목록 조회 개선 후 측정" 참고)

### 목록 조회 개선 후 측정 (이슈 #22)

적용: `playlists(owner_id, updated_at DESC, id DESC)`, `playlists(subscriber_count DESC, id DESC)`, `subscriptions(subscriber_id, playlist_id)`, `pg_trgm` GIN 인덱스(`lower(title)`, `lower(description)`)

- 스레드 덤프로 확인(풀 2개, 팔로우 10명 실행 중): 팔로우 저장(`FollowSaver.save`)의 커밋 처리 단계(`triggerAfterCompletion`) 안에서 알림 리스너(`NotificationDomainEventListener.handleUserFollowed` → `NotificationEventListener.handleNotification`)가 `NotificationService.save`(`REQUIRES_NEW`)를 호출하고, 이 호출이 새 연결을 얻으려고 `HikariPool.getConnection`에서 대기 중. 팔로우 저장 트랜잭션의 연결이 아직 반납되지 않은 상태에서 알림 저장용 두 번째 연결을 요청하는 구조라 풀이 작으면 서로 기다리며 30초 제한에 걸림.
- 같은 덤프에서 `FollowServiceImpl.follow`의 사전 조회(`findExistingFollow`)와 `findFollowDto`(팔로우 여부 조회), `FollowSaver.save`(저장)도 연결을 기다리는 스레드로 확인됨.
- 판단: 테스트 설정이 아니라 **팔로우→알림 이벤트 연결 구조 문제**(팔로우·알림 도메인 공동). 서버 로그의 `알림 저장 실패`·`Connection is not available` 줄 수는 별도 집계하지 않음.
- 참고: `FollowServiceImpl.follow()` 자체에는 `@Transactional`이 없어 그 메서드가 연결을 쥐는 구조는 아님.
