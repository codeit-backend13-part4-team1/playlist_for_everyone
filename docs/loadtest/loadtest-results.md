### 목록 조회 개선 후 측정 (이슈 #22)

적용: `playlists(owner_id)`, `playlists(subscriber_count DESC, id DESC)`, `subscriptions(subscriber_id, playlist_id)`, `pg_trgm` GIN 인덱스(`lower(title)`, `lower(description)`)

개선 전후를 같은 조건(20명 · 접속 120초 · 워밍업 1회 후 기록 1회 · 같은 데이터와 파라미터)으로 다시 측정한 결과는 별도 문서에 정리했다. EXPLAIN (ANALYZE, BUFFERS) 원문, 인덱스별 적절성 판단, 쓰기 비용 확인 방법과 한계도 그 문서에 있다.

> 소유자 필터의 JMeter 후 값(38 ms)은 변경 전 복합 인덱스 `(owner_id, updated_at DESC, id DESC)` 상태에서 측정했다. <br>
> 단일 `(owner_id)` 인덱스로 변경한 뒤에는 EXPLAIN으로 같은 실행 계획과 buffers(목록 12, count 9)를 확인했고, JMeter는 재측정하지 않았다.
- 기본 정렬, 키워드(흔한 2글자 단어), 커서 2페이지는 이번 인덱스의 대상이 아니며 차이는 노이즈 범위로 본다.
- 2글자 이하 키워드는 trigram 인덱스를 쓸 수 없어 전체 스캔이 그대로이며 이번 범위에서 개선하지 않았다.
- 쓰기 비용: 앱 수준 측정은 최신 dev의 알림 연동에서 커넥션 풀 고갈이 발생해 사용할 수 없었고, DB 수준 벤치에서는 개선 전후 구분 가능한 차이가 없었다.

- 스레드 덤프로 확인(풀 2개, 팔로우 10명 실행 중): 팔로우 저장(`FollowSaver.save`)의 커밋 처리 단계(`triggerAfterCompletion`) 안에서 알림 리스너(`NotificationDomainEventListener.handleUserFollowed` → `NotificationEventListener.handleNotification`)가 `NotificationService.save`(`REQUIRES_NEW`)를 호출하고, 이 호출이 새 연결을 얻으려고 `HikariPool.getConnection`에서 대기 중. 팔로우 저장 트랜잭션의 연결이 아직 반납되지 않은 상태에서 알림 저장용 두 번째 연결을 요청하는 구조라 풀이 작으면 서로 기다리며 30초 제한에 걸림.
- 같은 덤프에서 `FollowServiceImpl.follow`의 사전 조회(`findExistingFollow`)와 `findFollowDto`(팔로우 여부 조회), `FollowSaver.save`(저장)도 연결을 기다리는 스레드로 확인됨.
- 판단: 테스트 설정이 아니라 **팔로우→알림 이벤트 연결 구조 문제**(팔로우·알림 도메인 공동). 서버 로그의 `알림 저장 실패`·`Connection is not available` 줄 수는 별도 집계하지 않음.
- 참고: `FollowServiceImpl.follow()` 자체에는 `@Transactional`이 없어 그 메서드가 연결을 쥐는 구조는 아님.

  - 코드: 조건에 맞는 모든 콘텐츠를 DB에서 읽고(전체 읽기), 모든 콘텐츠 ID(11,000개)를 Redis 스크립트 한 번에 넘겨 시청자 수를 구한다.
  - Redis 슬로로그: 이 스크립트(키 11,000개) 호출이 **211~256ms씩** 걸린다. Redis는 명령을 하나씩 처리해 그동안 다른 명령(로그인의 세션 처리 포함)이 대기하고, 앱의 Redis 응답 제한(3초)을 넘으면 시간 초과가 난다.

### 에러 원인 대조 (검색 측정의 500 합계 293건)

| 원인 | 건수 | 해당 실행 |
|---|---|---|
| DB 연결 풀 고갈 (로그 일치) | 81 | 부하 1차 12, 부하 2차 4, S4 단독 1차 65 |
| Redis 명령 시간 초과 (`RedisCommandTimeoutException`, 로그 212건과 일치) | 212 | 평시 1·3·4차 27, 부하 1차 1, S4 단독 2차 184 |

- 서버는 Redis 시간 초과를 처리하지 못해 500으로 응답한다(`처리되지 않은 서버 오류`).
- S4 단독 2차에서 로그인이 처음부터 실패한 이유(1차 직후 Redis 대기열 등)는 확인하지 못했다. 측정 후 로그인 확인(10명)은 정상이었다.
